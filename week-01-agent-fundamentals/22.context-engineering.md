# Lecture Note: 22. Context Engineering

## Introduction

Welcome to Week 1, Day 5. As we conclude the first week and our Digital Twin project, we transition from the "mundane reality" of agent loops to the sophisticated discipline of **Context Engineering**. While prompt engineering was once the primary focus of LLM interaction, the rise of agentic AI has shifted the emphasis toward managing the entire context window—the totality of information sent to the model to achieve a specific goal.

## I. From Prompt Engineering to Context Engineering

In the early days of LLMs, "Prompt Engineering" was a highly sought-after skill, often commanding significant salaries. However, as systems have become more complex, the focus has evolved.

- **Prompt Engineering**: Focused on the specific phrasing of the user's request.

- **Context Engineering**: Focuses on orchestrating all the information that enters the LLM's context window, including system prompts, tool descriptions, external data (RAG), and memory.

## II. The Anatomy of Context (Phil Schmid's Framework)

A year ago, Google engineer Phil Schmid introduced a diagram that has since become a standard for understanding context engineering. It breaks down the context window into several overlapping "bubbles" of information:

| Component | Description |
| --- | --- |
| **System Prompt** | The overall framing, role, and style of the agent. |
| **Instructions** | Specific, high-level directives on what the agent must achieve. |
| **User Prompt** | The current, active message from the user. |
| **Available Tools** | JSON-based descriptions of the functions the agent can call. |
| **Structured Outputs** | JSON schemas that force the LLM to respond in a machine-readable format. |
| **RAG / Agentic RAG** | Retrieval of relevant external data injected into the prompt, often via tools. |
| **Short-Term Memory** | The conversation history (User/Assistant turns) and current session state. |
| **Long-Term Memory** | Information retrieved from prior interactions, typically accessed through tools. |

## III. Practical Application in the Digital Twin

In our Digital Twin project, we have already performed significant context engineering by injecting external data into the system prompt.

### A. Injecting External Knowledge

We used Python's f-strings to dynamically build a system prompt that included:

1. **Personal Summary**: A text file (`summary.txt`) providing the agent's core identity.

1. **LinkedIn Profile**: Unstructured data extracted from a PDF (`linkedin.pdf`) to provide professional context.

### B. Defining Behavioral Boundaries

Context engineering also involves setting rules to prevent the agent from hallucinating or going off-topic. For example, our rules explicitly instructed the agent to:

- Stay in character as a digital twin.

- Avoid non-career-related questions.

- Admit ignorance rather than making up an answer.

## IV. The "Experimentation" Mindset

There is no single "correct" way to engineer context. The effectiveness of an agent depends heavily on its specific task and the underlying model.

- **Iteration**: The process involves developing a test set, evaluating performance, and experimenting with different context configurations.

- **Ambiguity**: The boundaries between system prompts, memory, and RAG are often fluid. Information might be shoved into the system prompt or retrieved dynamically via a tool depending on the size of the data and the model's capabilities.

## V. Conclusion

Context engineering is the art and science of providing an LLM with exactly the right information at the right time. By mastering the orchestration of tools, memory, and external data, we move beyond simple chatbots toward truly capable agentic systems. As we progress into Week 2, we will see how specialized frameworks like the OpenAI Agents SDK further simplify this process through high-level abstractions.
