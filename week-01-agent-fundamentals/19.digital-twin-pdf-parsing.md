## I. Groundwork and Environment Preparation

Before building the agent loop, we must prepare the knowledge base that the digital twin will utilize.

### A. Data Sources

The digital twin requires two primary inputs stored in a subfolder named `twin`:

1. **`linkedin.pdf`**: A PDF export of a LinkedIn profile or a standard resume.

1. **`summary.txt`**: A short, text-based summary providing personal context (e.g., name, core philosophy, or even personal quirks like a dislike for cheese).

> **Important Technical Note**: Filenames must be strictly **lowercase**. While Windows and macOS are often case-insensitive, deployment environments (typically Linux) are case-sensitive. Using lowercase prevents "sneaky" deployment errors.

### B. Required Packages

We utilize two specialized libraries for this implementation:

- **`pypdf`**: A popular Python library for reading and extracting text from PDF files.

## II. PDF Parsing and Data Extraction

Extracting text from a PDF involves iterating through its pages and "yanking" out the raw content.

### A. Implementation

```python
# Initialize the PDF reader
reader = PdfReader("twin/linkedin.pdf")
linkedin_text = ""

# Iterate through pages and extract text
for page in reader.pages:
    text = page.extract_text()
    if text:
        linkedin_text += text

# Read the personal summary
with open("twin/summary.txt", "r", encoding="utf-8") as f:
    summary_text = f.read()
```

### B. Handling Unstructured Data

The extracted text from a PDF is often "messy," with skills, job titles, and dates meshed together. However, a significant advantage of Large Language Models (LLMs) is their ability to interpret and structure such **unstructured data** intelligently, making rigorous pre-processing unnecessary.

## III. Foundational LLM Concepts: The Sidebar

To build a digital twin that "remembers" a conversation, we must master three foundational concepts.

### A. The System Prompt

The system prompt sets the **overall framing**, role, and style of the LLM. It is the part of the input sequence that tells the model *how* to behave (e.g., "You are a helpful assistant" vs. "You are a snarky assistant").

### B. Conversation History

LLMs do not just take a single message; they can process a list of dictionaries representing the to-and-fro of a dialogue. This list is the **conversation history**.

### C. The Illusion of Memory (Statelessness)

LLMs are inherently **stateless**. Every call to an API like OpenAI is independent and has no memory of previous interactions.

- **The Trick**: To give the *illusion* of memory, the developer must send the **full conversation history** back to the LLM with every new user message.

- **Cost Implication**: You pay for the input tokens of the entire history with every call, but this is necessary for the model to generate a contextually relevant and intelligent response.

**Example: Demonstrating Statelessness vs. History**

```python
# Call 1: LLM learns the name
messages = [
    {"role": "system", "content": "You are a helpful assistant"},
    {"role": "user", "content": "Hi, my name is Ed"}
]
# Response: "Hi Ed!"

# Call 2: LLM forgets (Stateless)
messages = [{"role": "user", "content": "What's my name?"}]
# Response: "I don't know your name."

# Call 3: LLM "remembers" (History provided)
messages = [
    {"role": "system", "content": "You are a helpful assistant"},
    {"role": "user", "content": "Hi, my name is Ed"},
    {"role": "assistant", "content": "Hi Ed!"},
    {"role": "user", "content": "What's my name?"}
]
# Response: "Your name is Ed."
```
