# Lecture Note: 10. Agentic Design Patterns

## Introduction

Building upon our understanding of what constitutes an AI agent, this lecture delves into **agentic design patterns**. These patterns, notably articulated by Anthropic in their seminal blog post "Building Effective Agents," provide conceptual frameworks for structuring LLM-powered systems. It is crucial to preface this discussion with a caveat: unlike the rigid design patterns found in mature software engineering, these agentic patterns are indicative and thought-provoking rather than prescriptive. They offer common approaches observed in production systems, often appearing in combination rather than in isolation.

## I. Workflow Design Patterns

Anthropic identifies five primary design patterns for **workflows**, which, as discussed previously, are agentic systems characterized by predefined paths and testable execution flows, even if LLMs make decisions along these paths.

### A. Prompt Chaining

**Prompt chaining** involves breaking down a larger, complex task into a sequence of smaller subtasks. The output from one LLM call serves as the input for the subsequent LLM call, creating a linear progression towards the overall solution.

- **Mechanism**: An initial LLM processes a part of the problem, its output is then fed into a second LLM, and so on, until the final output is generated.

- **Example**: The Day One lab, where an LLM generated a question, another answered it, and a third evaluated the answer, is a direct application of prompt chaining.

- **Role of Code**: Python code typically manages the flow between LLM calls, passing outputs as inputs and potentially making minor decisions.

### B. Routing

**Routing** utilizes an LLM to intelligently direct an incoming request to the most appropriate subsequent LLM or specialized prompt. This pattern is particularly useful for achieving **separation of concerns** and optimizing performance by leveraging LLMs tailored for specific domains.

- **Mechanism**: A primary "router" LLM analyzes the input and decides which specialized LLM (or a prompt designed for a specific context) should handle the request.

- **Example**: A customer support agent where an initial LLM classifies a query as "technical," "business," or "other," and then routes it to an LLM specifically fine-tuned or prompted to address that category.

- **Benefit**: Prevents overloading a single LLM with diverse knowledge and improves the relevance and accuracy of responses.

### C. Parallelization

**Parallelization** is a design pattern where a problem is decomposed into independent sub-problems that can be processed concurrently by multiple LLMs. The results are then aggregated by code.

- **Mechanism**: Our Python code (not an LLM) breaks down the initial input, distributes these sub-problems to several LLM calls in parallel, and then collects and synthesizes their individual outputs into a final result.

- **Role of Code**: The orchestration (breaking down and aggregating) is handled by conventional code, while LLMs perform the individual processing tasks.

### D. Orchestrator Worker

The **Orchestrator Worker** pattern is an advanced form of parallelization where an LLM dynamically manages the decomposition and synthesis of tasks. Unlike simple parallelization, the orchestrator and aggregator roles are themselves performed by LLMs.

- **Mechanism**: An "orchestrator" LLM receives a complex task and dynamically determines how to break it into smaller, parallelizable subtasks. These subtasks are then sent to "worker" LLMs. Finally, another LLM (the "synthesizer") aggregates the results from the worker LLMs into a coherent output.

- **Key Distinction from Parallelization**: The decision-making for task decomposition and result aggregation is delegated to LLMs, making the workflow more dynamic and LLM-driven, yet still within a predefined structural path.

### E. Evaluator Optimizer (LLM as a Judge)

Also known as **LLM as a Judge**, this pattern involves using one LLM to generate a solution and another, separate LLM to evaluate its quality or correctness. This creates a feedback loop for refinement.

- **Mechanism**: An "LLM Generator" produces a solution. An "LLM Evaluator" then assesses this solution. If the evaluation is negative (rejection), the task may be sent back to the generator for revision. If positive (acceptance), the solution proceeds to output.

- **Benefit**: Enhances the reliability and quality of LLM outputs by incorporating an automated review process.

## II. Agent Design Pattern

In contrast to workflows, the design pattern for **agents** emphasizes open-ended, iterative execution with feedback loops, aligning with the definition of an LLM with tools in a loop to achieve a goal.

- **Mechanism**: An LLM receives input (e.g., from a human), interacts with an environment using various tools, observes the outcomes of its actions, and continuously refines its strategy within a loop. This process continues until the LLM determines that its goal has been achieved.

- **Characteristics**: No strictly predefined paths; dynamic decision-making; continuous interaction with the environment; inherent feedback mechanisms.

- **Relationship to Definition**: This pattern directly embodies the core definition of an AI agent: an LLM leveraging tools within an iterative loop to accomplish a specific objective.

## III. Conclusion and Practical Application

These agentic design patterns are conceptual tools to guide the development of LLM-powered systems. While they are not rigid rules, understanding them helps in structuring complex AI applications. Often, real-world systems incorporate elements from multiple patterns. For commercial production systems, workflows are frequently favored due to their inherent repeatability and testability, even when LLMs are integral to decision-making. The distinction between workflows and agents, particularly the open-ended nature of the latter, remains a helpful mental model for AI engineers.
